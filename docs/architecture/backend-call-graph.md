## Source Migration and RLS Observations

- `supabase/migrations/20261015133516_add_project_scope_to_resource_tables.sql` adds nullable `project_id` foreign keys with `ON DELETE SET NULL` to services, products, menu items, pricing plans, offers, testimonials, portfolio projects, availability slots, content types, and content entries. It adds `(business_id, project_id)` indexes, but performs no backfill, RLS enablement, grants, or policy rewrite.
- Earlier source policies for catalog tables use business membership or public-active/public-available predicates, not project scope. For example, products select allows `is_active = true`, services exposes active rows or business members, and menu items exposes available rows. The project-scope migration does not change those policies. These may be intentional business-level/public projections, but they do not prove project isolation for direct Data API callers.
- `cms-records` manually filters project-bound reads to `project_id = project OR project_id IS NULL`; it writes the requested project ID and checks business/project relationships. Null-project legacy rows are therefore visible through shared-adapter project reads; treating all null rows as shared requires ownership evidence and an explicit policy.
- The new foreign keys use `ON DELETE SET NULL`. Since null rows participate in shared-legacy reads, deleting a project could make formerly project-owned rows indistinguishable from legacy rows. Deletion/backfill semantics need a deliberate migration plan before relying on this FK behavior.
- The enterprise content migration enables RLS and revokes direct `anon`/`authenticated` table grants for content types, entries, revisions, and publish events; supported access is through server-side CMS commands. Deployed grants/policies may differ and were not queried.
- These are repository migration observations only. They do not establish which migrations ran remotely or whether later hotfixes changed the effective policy state.

## Linked Supabase CLI Audit

### Resource schema and ownership

- All ten scoped resource tables have a nullable `project_id` UUID foreign key to `projects(id)` with `ON DELETE SET NULL`. Each table has RLS enabled, but `FORCE ROW LEVEL SECURITY` is false.
- Aggregate row counts show 104 records across the ten tables, all with `project_id IS NULL`: 77 `availability_slots`, 16 `products`, and 11 `services`. `menu_items`, `pricing_plans`, `featured_offers`, `testimonials`, `portfolio_projects`, `content_types`, and `content_entries` each currently have zero rows. This confirms the nullable-column migration ran but existing catalog/availability rows were not backfilled to projects.
- Public SELECT policies are business-wide rather than project-filtered: active products, active services, available menu items, active pricing plans, all featured offers, all portfolio projects, all testimonials, and all availability slots. Authenticated writes use business membership/permission policies. No project predicate appears in these resource-table policies.
- `anon` has table-level DML grants on products, menu items, pricing plans, featured offers, testimonials, and portfolio projects, while the observed RLS policies expose only SELECT to the public role. Writes were not attempted; effective denial depends on RLS and must not be inferred from grants alone.
- `content_types` and `content_entries` have RLS enabled with direct table grants limited to `postgres` and `service_role`; no browser-role policies appeared in the queried policy set.

### Backend bindings and resolver mismatch

- `connected_supabase_projects` has RLS enabled, no `anon`/`authenticated` table grants, and zero rows. There are currently no connected/dedicated backend bindings in this project.
- Its live columns are `connection_id`, `business_id`, `unison_project_id`, `project_ref`, `project_url`, encrypted publishable/secret keys, `schema_version`, `provisioning_status`, `backend_manifest`, and `health_status`. The live table has no `site_id`, `mode`, `provider`, or `provider_project_ref` columns.
- The initial local `project-backend` source selected `site_id` from `connected_supabase_projects`, but the live table has no such column. The local source now resolves `site_id` through `projects`/`sites` and checks the binding's `business_id` and `unison_project_id`; Supabase CLI deployed it as active function version 22 with `verify_jwt=false` preserved. Dedicated CRUD is still not end-to-end verified because there are zero live bindings.
- Neither `resolve_project_backend` nor `resolve_published_site_backend` exists in any live database schema, and neither function name appears in repository migrations. The client resolver and published backend helper call these RPCs, so backend resolution currently has no matching deployed database function.

## Phase 1 implementation status

- Added `src/services/project-backend/runtimeProtocol.ts` as an additive v2 envelope and adapter over `ProjectBackendResolver` / `ResourceRuntime`; existing v1 entrypoints are unchanged.
- Resource keys resolve through `resourceRegistry`; arbitrary table names are rejected. Required project/site/business context is validated, and dedicated failures never route to the shared adapter.
- Errors are returned in a structured envelope. `asset.link`, `intent.execute`, filtered list queries, and optimistic record-version checks explicitly return `UNSUPPORTED` until their existing domain owners are wired.
- `operationId` is returned as correlation only. Existing storage paths do not persist operation receipts, so the v2 wrapper does not claim idempotent writes. Server auth/membership remains authoritative; caller-supplied `actorKind` is not trusted for authorization.
- Focused validation after the change: 9 backend/runtime/industry/storage contract test files passed (247 tests), `npm run type-check` passed, targeted ESLint passed, and Deno check passed for `project-backend`.
- V2 now maps the missing `resolve_project_backend` / `resolve_published_site_backend` RPC schema-cache error to a non-retryable `BACKEND_UNAVAILABLE`; it does not fall back to shared storage.
- Added fake-backed backend-to-UI contracts across all ten canonical industries. Source-owned titles make zero business-data calls; derived catalog seed targets go through `ResourceRuntime` and project into the canonical `CatalogCardViewModel`; each primary intent is registered, capability-owned, and backed by local Edge Function files. Shared and dedicated list/get/create/update/delete operations are exercised for every derived industry surface; each mode stays on its selected adapter. Portfolio/SaaS static fixtures and salon/menu resource fixtures remain explicit. The SaaS fixture rejects an unregistered generic tenant table rather than asserting a nonexistent SaaS adapter.
- Dedicated catalog evidence is limited to the client facade with fake resolver/backend adapters. The live project has zero connected bindings, and the deployed `project-backend` Edge Function has not been source-hash or end-to-end parity verified.
- Aligned commerce capability declarations and provisioning readiness with the published runtime's existing `create-order-checkout` controller instead of the authenticated account-subscription `create-checkout` endpoint.
- Nonprofit donation checkout remains an explicit contract gap: `donation.start` declares `stripe-checkout`, whose current generated controller targets product `create-order-checkout`; the donation capability still references account `create-checkout`. Neither is a domain-correct donation payment contract. Do not claim donation checkout parity until a dedicated typed handler and UI payload contract exist.
