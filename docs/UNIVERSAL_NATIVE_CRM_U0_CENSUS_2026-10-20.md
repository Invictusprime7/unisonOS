## Writer Consolidation Implemented Locally

- Contacts, leads, deals, workflows, and automations in [resourceAdapters.ts](../src/services/resources/resourceAdapters.ts) now share scoped browser CRUD through ResourceRuntime. Mutations invoke the authenticated `crm-command` function; reads remain RLS-filtered client queries. Writable fields are filtered by the resource registry; business/project scope comes from `ResourceContext`, not submitted values. Lead UI `status` maps to stored `stage`.
- CRM screens, `useCRMActions`, and the visual workflow builder no longer mutate CRM tables directly. Same-business shared contacts remain visible/editable within project workspaces; other resources remain project-filtered.
- Public and privileged Edge Function writes for contacts, leads, activities, and workflow metadata use the same [canonicalCrm.ts](../supabase/functions/_shared/canonicalCrm.ts) implementation invoked by `crm-command`. It validates business/project agreement, supports project-only records, scopes updates and references, and writes canonical `stage`/`type` fields. Migrated callers include public lead/form/quote intake, intent-action/router/exec, automation-runtime, workflow-job-processor, workflow-cron, agent-runner, GHL reactions, and booking linkage.
- Removed the fallback inserts into missing `public.leads` and `crm_deals` from public quote paths. Quote requests are CRM leads/activities; deals remain an optional workspace capability.
- Added PGlite tests for both linked workspace-shaped and older UI-era CRM schemas. The local migration draft adds tenant scope, compatibility aliases, business-scoped contact email uniqueness, deals storage, scoped RLS, and workflow run/job column bridges.

Workflow run/job rows remain workflow-engine state written by workflow orchestration handlers, not contact/lead/activity mutations. Atomic booking creation remains scheduling-owned; its CRM linkage uses the shared CRM commands after booking commit and remains best-effort.

The migration and changed Edge Functions have been deployed to linked UNISON. CRM tables were empty before deployment; the existing automation and 1,120 projects (including 25 without `business_id`) were preserved. A rollback-only CLI transaction inserted synthetic CRM rows, switched to the authenticated database role with two existing project-owner subjects, checked visibility/denial, then rolled back successfully. This validates deployed RLS expressions but does not verify JWT signature handling or invoke the Edge Function as a browser session.

The local migration draft follows the milestone contract: business is the tenant owner; project/site/location remain separate; `workspace_id` is retained but nullable; `stage` and `type` are canonical; workflow legacy aliases are synchronized during transition; and deals are an optional sales capability explicitly installed because the current workspace exposes it. ## Applied Migration Contract

Follow the milestone's explicit scope model: `business_id` is the tenant owner; `project_id` identifies the site/project when attribution is site-specific; `site_id` and `location_id` remain separate where present. Treat `workspace_id` as a legacy authorization scope, not an inferred substitute for business or project identity. New commands must receive scope from trusted project/business resolution and enforce project-to-business consistency in the database.

For compatibility, the first migration should be additive and staged with matching client/Edge Function adapters. Preserve legacy columns until every reader/writer is mapped; do not rename or drop `stage`, `type`, `actions`, `active`, or workspace-based policies in the same step that adds business/project access. The local CRM API currently expects lead `status`, activity `activity_type`, and workflow `steps`/`is_active`; select one canonical representation for each and make temporary adapters explicit rather than maintaining silent dual writes. Keep `crm_workflows` (sequence definitions/runs) and `crm_automations` (event rules) as distinct persisted engines until their lifecycle migration is tested.

`crm_deals` is installed by the local draft only as the already-exposed sales-pipeline capability, not as universal CRM core. The legacy `crm_pipelines` JSON-stage manager has had its direct writes removed from the generic CRM manager; remaining reads should be retired or explicitly supported in a separate compatibility pass. `crm_stages` is not recreated.

Because the inspected CRM tables are empty, the migration avoids CRM-row backfills and includes shape guards, project/business checks, and replacement RLS. It passed PGlite tests against a linked-schema fixture and a legacy UI-schema fixture. This does not replace an isolated Supabase test for Auth helpers, grants, or deployment configuration.

**Deployment evidence:** CLI dry-run listed only `20261020232357_crm_business_project_compatibility.sql`; the linked push applied it with vault updates skipped. All 14 affected Edge Functions are ACTIVE, preserving their previous `verify_jwt` modes, including JWT-protected `crm-command`. CLI security/performance advisors returned no CRM-specific notices. A rollback-only live CLI RLS test passed for owner-one/owner-two project visibility, shared contacts, and cross-business lead insert denial. Local Supabase remains unavailable without Docker/Podman, so signed-JWT Edge invocation and public visitor tests remain follow-up work.

## U2 Unified Resource Command Progress

- `BusinessCatalogEditor` now reads and writes through `ResourceRuntime` instead of calling `cmsRecordService` directly. Create/update/delete use typed `ResourceDataOp`; update includes the values observed when editing, and ResourceRuntime owns writable-field filtering, concurrency checks, telemetry, and invalidation. Business scope is supplied as context rather than copied into record values.
- CRM workspace and Preview resource edits already use ResourceRuntime adapters; this closes the Business Catalog admin UI bypass while retaining the catalog/content/CRM-specific server adapters behind the shared dispatcher.
- `cms-records` now writes mutation audit rows to `resource_mutation_audit`; the table is RLS-enabled with no anon/authenticated privileges and service-role SELECT/INSERT only. The Edge write is awaited, while audit failure is logged without turning a completed mutation into a retry-inducing error. This is durable audit, not an atomic outbox.
- Content entry updates/transitions now pass the observed `updated_at` to a service-role-only compare-and-set RPC. It locks the entry row before comparing the version, then delegates to the existing atomic entry/revision/publish-event command; stale writes return HTTP 409 before a new revision is created.
- Content-entry create/update/transition now use an audited wrapper around the existing command, so mutation audit, entry write, revision, and publish event commit or roll back together. Stale compare-and-set conflicts do not create an audit row or revision.
- Content mutations now accept an idempotency key. The audit row is the receipt, uniquely indexed by business/key with a request fingerprint; identical retries return the prior record without another revision/audit, while key reuse with a different payload is rejected. Concurrent duplicate inserts resolve through the unique index and transaction rollback path. No UPDATE privilege was added to the append-only audit table.
- Canonical CRM contact creation also has a natural-key dedupe path through the unique `(business_id, email_key)` index; duplicate lead contact inputs resolve to the existing contact. This does not make the lead command itself idempotent.
- The audit, compare-and-set, atomic content-audit, and content idempotency migrations were applied to linked UNISON, and `cms-records` is ACTIVE at the latest version. Rollback-only tests verified service-role audit insertion, current/stale content updates, audit/revision atomicity, idempotent create/update replay, key-reuse rejection, and cleanup; no probe rows persisted.
- Focused ResourceRuntime, cross-industry editing, Business Center routing/audit, content idempotency/CAS, and CRM adapter tests pass: 38 tests across four suites. No existing business/catalog/content records were changed.
- **U2 gate remains open.** Idempotency receipts are implemented for content commands; contacts have natural-key dedupe, but leads/deals/catalog commands lack general request receipts. A generalized transactional outbox, workflow retry behavior, and authenticated end-to-end contact/catalog parity across separate UIs still need verification before declaring the unified kernel complete.
