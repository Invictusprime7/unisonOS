# Directory rules
- Selected text edits use the shared literal-leaf JSX mutation and clicked-text anchoring; preserve inline wrappers/icons and refuse dynamic data expressions. Why: rejecting every nested tag blocked edits, while replacing only the first text run left stale formatted copy behind.
- Builder source output is projected only from App Builder candidates and applied via `onApplyToVFS`; there are no prose/file extraction or legacy generated-code callbacks. Why: a second result path can report success before the canonical save reaches preview.
- The floating edit toolbar's AI box is a front-end of the AI Builder: it dispatches `unison:builder-send` {prompt, target} and never calls AI itself; why: one agent owns context, button-destination checks and saves.
- Direct toolbar edits (style/text/image/attrs/delete/duplicate/move) commit via `commitBuilderFiles` inside `runExclusive('toolbar')`, then run post-save intent verification; why: the old bridge bypassed the save queue, ignored edits in non-active files and never checked buttons.
- Toolbar move/delete/duplicate dispatch through the source executor; styles/hide dispatch through presentation, matching the shared property-owner resolver. Why: an unreachable presentation move case rejected both reorder controls before the host save handler.
- Toolbar and Builder image generation run through the AI Builder's image extension (`ai-code-assistant` mode `image-generate`, `imageExtension.ts`) with the clicked element's site context, then save via the canonical image-replace path; why: images must be site-aware like every other Builder edit.
- Toolbar image swaps resolve the owning file by the current image link first (unique literal across source), then by identity hints (owner file, link/alt/text evidence, page import graph) in `findUniqueSourceMutation`; ambiguity still refuses; why: loose selector matches made swaps hit unrelated pages like Shop or a carousel.
- Elements with no picture (sections, cards) get one only after the user picks placement (background vs image inside) and, for repeated cards, scope; placement rides `ImageGeneratedDetail.placement` into WebBuilder's one save handler; why: the user asked to be asked each time, and one handler keeps upload, URL and AI paths identical.
- The preview bridge's `findImageTarget` counts only the clicked element itself (an <img>, a bare wrapper of one <img>, or its own url() background), never nested or ancestor pictures; why: sections that merely contained a shared image were treated as that image, so saves matched several files.
- Placement edits (add background / image inside) resolve the element through `anchoredFinder`: a position selector is trusted only if the matched element contains the clicked text, else the unique text run locates it, else refuse; `mutateJSXStyles` layers updates over styles it cannot parse rather than rewriting them; why: nth-of-type selectors hit the wrong section and lossy re-serialization wiped layout styles.
