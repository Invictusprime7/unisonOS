# Unison App Builder: Dynamic Sites

Use the imported DREAM Design site as a behavioral reference for complete interactions, not as a second implementation or a visual-only target:

- Workspace source: `docs/knowledge/references/dream-design/dream-design/`
- Original archive: `docs/knowledge/references/dream-design-source.zip`
- `src/project-components/site/SiteNav.tsx` shows internal route links, active-route state, mobile drawer state, and a consultation callback.
- `src/project-components/home/ConsultationModal.tsx` shows a controlled modal with locally managed form fields and a submission action.
- `src/components/formRuntime.ts` shows published form interception, runtime configuration checks, payload context, idempotency, disabled-submit state, reset, and success/failure feedback.
- `public/_redirects` is the reference for deployment-level route fallback and redirects; distinguish these from in-app navigation.

## Canonical Unison Ownership

- `LauncherWizard` captures intent; it does not author or mutate VFS source. `UnisonAppBuilder` is the sole fresh-launch author.
- The canonical platform owns routes, capabilities, intents, bindings, and protected infrastructure. Do not generate parallel pages or a second interaction engine.
- Add or change intent definitions in `src/platform/core/intentSurfaceRegistry.ts`; `src/platform/core/coreIntents.ts` is a derived compatibility surface.
- Trace execution through `src/runtime/intentRouter.ts` and the registered handler/site-runtime adapter before wiring a frontend interaction. Respect the handler declared by the registry; do not route an intent to a convenient but incorrect backend.
- Keep Composer contracts mirrored between `src/contracts/aiComposerContract.ts` and `supabase/functions/_shared/aiComposerContract.ts` when a change affects those contracts.
- Canonical VFS mutations go through `runBuilderAiMutation` and `commitMutation`. Preserve saved project source and require normal signed-in acceptance.

## Interaction Workflow

1. Inspect the reference component and identify its trigger, state transition, payload, completion state, failure state, and route behavior. Treat reference code as evidence, not as permission to copy its transport or bypass Unison contracts.
2. Reuse an existing canonical intent whenever it expresses the action. If none fits, add the smallest appropriate definition to the canonical registry and wire its registered handler end to end.
3. Wire generated UI to a real runtime action. Intent attributes alone, an inert `href="#"`, a toast-only handler, or a demo form are not proof that the behavior works.
4. For overlays, connect the trigger to the intended open action and provide working close paths, focus/accessibility behavior, and meaningful submit/error states. Keep local presentation state local; route durable actions through the canonical binding.
5. For navigation and redirects, distinguish client-side route changes, external navigation, anchor scrolling, and host-level redirect/rewrite rules. Confirm that destinations exist and preserve the app's router and published-site behavior.
6. For forms, use real submit semantics and named fields; validate and serialize the expected payload; prevent duplicate submits; show pending, success, and recoverable error states; and verify the configured runtime/backend actually accepts the submission. Do not silently downgrade an unconfigured form to a fake success.
7. Check preview and published behavior separately where transports differ. A preview-only success is not evidence that the published binding works, and vice versa.
8. Add or update a focused behavior test for the changed intent or interaction, then run the narrowest relevant test/typecheck before broad validation.

## Completion Criteria

- Each visible action has a traceable canonical intent/binding or is explicitly local UI state.
- The runtime selected by the intent registry receives the expected route or payload and returns observable success/failure behavior.
- Overlay, redirect/navigation, and form flows work in their intended preview and published surfaces without unrelated source changes.
- Tests cover the specific interaction and do not rely only on checking for `data-ut-intent` strings.
