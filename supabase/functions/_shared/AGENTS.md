# Shared edge rules
- App Builder page writing, repair and Builder source edits use direct Gemini, then an optional direct Lovable gateway only when `LOVABLE_API_KEY` exists in the same project; stale model selections and other configured direct keys cannot introduce OpenAI/Anthropic. Other shared tasks retain their existing provider policy. Why: the owner explicitly requested their Gemini key instead of OpenAI on 2026-10-28, and the fallback must be directly configured in the project.
- Direct-Gemini composition leads with Gemini 3.8 Flash (`composerGeminiModel` in `_shared/providerRouter.ts`, mirrored in `runDirectGemini`), overridable by the `GEMINI_COMPOSER_MODEL` secret; the managed Gemini backup retains its existing explicit model rather than switching to another provider.

- Direct Gemini calls send the turn's `reasoning_effort` (Gemini 3 maps "none" to "low", retrying once without it if rejected); Composer batches and repairs default to low. Why: unset, Gemini 3 thinks at its slow default and large-page repairs timed out.
- `AI_PROVIDER_MODE=gemini-primary` makes Gemini priority explicit; weighted distributions and explicit model selections must not move another provider ahead of configured Gemini. Lovable can never lead while any direct provider is configured. `GEMINI_COMPOSER_MODEL` controls composition; `GEMINI_MODEL` is the default for unspecified Gemini calls and must not replace explicit fallback model IDs.
- App Builder preserves its request budget and reserves a usable window for the optional direct Lovable fallback; do not introduce OpenAI attempts or cache timeouts to change provider priority. Why: Gemini leads while the configured direct fallback remains reachable.
- Builder source edits, App Builder page repairs and continuing section batches return SEARCH/REPLACE `<<<EDIT` blocks for existing files that `composerLane.ts` applies to the request's FILES before validation. Why: rewriting whole files produced 20–30k-token answers that outran the ~122 s provider window, even after every batch had succeeded.
- Builder source edits must use `<<<EDIT` hunks on existing files (FILE replace/create on an existing path is rejected in `composerLane.ts`); page-creation requests may only create new pages plus nav/footer edits, and read only the target + site chrome; scoped client reads skip transitive imports, theme and package files unless the instruction names them. Why: whole-file rewrites and bloated context outran the provider window.
- Composer requests pass `conformComposerRequest` (clip text, drop unwritable optional targets/oversized supporting files, never the page or edited files) on both client and edge; schema rejections return field-level `details`. Why: an opaque "Invalid composer request" blocked edits with no way to see which field failed.
